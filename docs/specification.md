# Functional specification

This is the normative behavior for the first reusable heiry release. [Architecture](architecture.md) describes enforcement and lifecycle; [testing](testing.md) defines implementation gates. [Roadmap](roadmap.md) tracks implementation status and evidence.

## S1. Scope and authoring costs

Use one leaf object containing its ancestors through anonymous value embedding. Support single inheritance, typed virtual and parent dispatch, extensible public/private interfaces, and independent objects with shared immutable schemas. Application constructors retain arbitrary signatures; object allocation and inheritance setup are separate.

Hierarchy declarations are receiver-free: their reusable metadata contains types, paths, contracts, and explicit operation registrations, never an application object, bound method, or object-capturing closure. Individual `Bind[T]` registration takes a typed-nil provider witness and retains the compiler check that the provider satisfies T. Grouped `BindGroup` registration associates one typed-nil pointer witness with several `Of[T]` operation tokens. The compiler checks the pointer argument but does not prove that the provider implements each token's interface; definition validation checks each association. Instance-specific pointer and ownership checks apply to both styles.

Grouped and individual registration describe the same per-operation bindings and must not infer overrides from a provider's method set. A malformed grouped call, including an empty group or invalid token, adds no bindings and records sticky receiver-free diagnostics; creating an unsuitable token does not panic. A well-formed group contributes per-operation entries to validation: valid entries can count toward coverage while invalid entries are reported, and no invalid definition can prepare a Plan. The declaration does not retain a caller's token slice. **Validation-time grouped checks do not weaken invocation typing:** either style resolves to typed interfaces through `Method[T]` and `ParentMethod[T]`, preserving compile-time argument/result checks and ordinary calls under S2, without reflective invocation.

Level handles stay attached to the level where they were created, including after later levels are added. Invalid fluent calls add no binding, retain only receiver-free structured diagnostics, and keep those errors visible on later validation; a corrected definition is needed to clear them. `Validate()` examines the current configuration without freezing it or creating a Plan. Later edits are checked on the next validation and cannot reuse an earlier validation result. The final declared node type must equal `Leaf` exactly, and the complete direct value-parent chain must be valid before leaf-relative node paths are accepted. Validation reports recorded diagnostics together with further errors that can safely be established. Invalid registrations do not satisfy contract coverage; when contract analysis is possible, every missing mandatory public and private method is reported. [Architecture](architecture.md#receiver-free-schema-declaration-api) defines the declaration signatures and enforcement.

A level after the root may name its parent field explicitly or be declared with `Extend` or `ExtendWith`, as approved in [ADR 0012](decisions/0012-additive-authoring-conveniences.md). Both infer the parent as the single direct anonymous value field whose type equals the preceding level's node type; `Extend` also inherits the preceding level's effective public and private contracts, while `ExtendWith` supplies them. Inference never guesses: no candidate or more than one is InvalidHierarchy, and the explicit form remains available. The inferred field's declared name, including an alias name, is recorded in the validated metadata and used exactly as a named one. An extension call with no preceding level adds no level, records a sticky InvalidDeclaration, and returns an inert handle; the root is declared with its contracts and an empty parent field. A level handle registers on its own level; `End` returns the definition, which adds the next level at the end of its chain and performs validation, preparation, initialization, and reference creation.

Authors supply canonical single-method interfaces, explicit registrations, bodies, directly embedded Node holders, and manually written public forwarders. Every public operation needs a forwarder on the public wrapper. Private operations need no public forwarder. This is an explicit cost of the handwritten API, not a hidden promise to synthesize aggregate interfaces at run time. The optional generator under [S10](#s10-optional-code-generation) can write these interfaces, registrations, references, and forwarders as ordinary source through the same API; it changes nothing the library requires.

The first reusable release must support multiple providers at one inheritance level, such as A1 and A2 supplying different operations. Fluent configuration must accommodate them.

### Fluent configuration

Hierarchy definition and behavior configuration must be intuitive, concise, readable, and naturally chainable, without unnecessary boilerplate. Make the hierarchy levels, their public/private contracts, and their explicit bindings clear at the point of configuration. Preparation, optional precomputation, and initialization should compose naturally with that style.

The following illustrates the intended programming style. It is pseudocode, not a mandatory API signature or an executable example; `...` stands for omitted configuration:

```go
NewHierarchy(c).
    NewLevel("A", &c.B.A).
        Contracts(...).
        Bind(...).
        End().
    NewLevel("B", &c.B).
        Contracts(...).
        Bind(...).
        End().
    NewLevel("C", c).
        Contracts(...).
        Bind(...).
        End().
    MustPrepare().MustPrecompute().MustInit()
```

The illustration does not replace the approved declaration, component-reference, and lifecycle signatures in [architecture](architecture.md#receiver-free-schema-declaration-api). Return the same configuration handle where appropriate, or a handle for the next stage so the chain can continue. Fluent syntax must accommodate individual and grouped registration, multiple providers per level, per-level contract extension, ordinary error handling, and both dynamic and precomputed dispatch.

The illustration does not select how a reusable hierarchy definition supplies a Plan to the object chain. That Plan may be prepared eagerly or lazily under [S6](#s6-validation-plan-preparation-and-reuse), without requiring a second hierarchy definition.

## S2. Native calls and dispatch boundary

Consumers call ordinary methods, e.g. `obj.Process(data, retries)`. The public wrapper resolves the most-derived implementation. Implementations use `Method[T](receiver.Node.Scope())` for virtual calls and `ParentMethod[T](receiver.Node.Scope())` for parent calls, then invoke a method on the returned typed interface. The holder methods `receiver.Node.Virtual[T]()` and `receiver.Node.Parent[T]()` are equivalent and resolve through the same scope. They are called through the provider's own directly declared holder field by its actual name, which is the alias name when the holder is embedded through an alias. The promoted spelling `receiver.Parent[T]()` is not a supported form: an application member of that name can make it fail to compile or silently replace it.

Preserve arbitrary arguments, variadics, multiple results, and ordinary application errors. No reflect.Value.Call, unsafe, method-name strings for invocation, source inspection, mutable execution cursor, constructor registry, or class registry is permitted. Structural reflection belongs in setup. Runtime type-identity lookup and type assertions are allowed.

Concrete calls follow Go selectors: `c.Process` selects C's body if declared there; `c.B.Process` may select A's promoted body. Converting an ancestor pointer to an interface does not change that. Direct calls bypass virtual resolution at entry; their bodies can still explicitly dispatch virtually. Calling `a.Validate` does not select B's override. Method/ParentMethod must not be advertised as interception of arbitrary Go calls.

## S3. Contracts and target validation

Public and Private are ordinary method-only interfaces. **Private means inheritance-internal API, not compiler-enforced protected access.** Each level supplies its effective public/private pair or inherits both unchanged; the root must supply both, including an explicit empty interface if needed.

Each child must be a structural superset of its parent's public contract and, independently, its private contract. Preserve exact parameter/result types and variadic status. Interface embedding is preferred. Reject narrowing, signature changes, or moving inherited operations between categories. Any public/private name collision is invalid, even with identical signatures. Identical repeated declarations within a single interface follow Go's native rules and denote one operation.

Use exported operation names and a single canonical single-method interface type for each operation across levels. Exact type aliases share identity; a separately defined but structurally identical interface is a different key and must not be registered as a second canonical type. Aggregate interfaces are contracts, not resolution requests. Reject unexported operations and unsupported constraint-only contracts.

A binding can implement only an operation declared in its own level's effective contracts. Descendants can introduce operations and override inherited ones. Every operation in the final target's effective contracts is mandatory. Intermediate levels may remain abstract; coverage is checked over the selected ancestry, not independently at every node. A standalone A checks only A; B checks A/B; C checks A/B/C. Descendants never satisfy a standalone ancestor target. There are no optional methods or try-parent API in this release.

For example, if B extends its private contract with Transform and only C implements it, standalone B is abstract while C can be complete. This is a behavioral illustration, not an existing example program.

Bodies should depend on their own effective contracts. Resolution keys come from the complete target: an ancestor can technically request a later capability on C but gets UnknownCapability on a smaller target without it. Validation does not inspect body dependencies or prove termination.

## S4. Implementation ownership: formal trust boundary

**A binding is an assertion by the programmer that the provider owns the intended implementation. The framework validates signature and physical ownership, but not method declaration origin.**

A typed `Bind[Validator]` registration for B can compile when B merely promotes A.Validate. Do not treat compiler satisfaction or reflection's method set as evidence of a new override. Empty registrations mean inherit; promoted bodies and forwarders do not create registrations automatically. Do not register wrappers or infrastructure as implementations.

Incorrect assertions may reenter the same body during a parent call and recurse indefinitely. Detection of declaration origin and proof of body termination are outside the guarantee.

## S5. State, structure, and providers

The hierarchy is a nonempty ordered chain of distinct named struct types. The final node is the target; each preceding node is exactly one direct anonymous value field of its child. Validate explicit parent field metadata, not declaration order or promoted methods. When a level is declared with an inferred parent under S1, validation first derives that metadata from the unique matching field and then validates it in the same way. Reject pointer inheritance (including nonnil pointers), nil nodes/providers, repeated levels/types, missing intermediate nodes, and ambiguous or nonanonymous parent edges.

Bind the actual embedded addresses; never allocate independent ancestors or copy their state. Unrelated composition fields contribute no methods automatically.

A level may register its node, multiple component providers, or both. A provider is a pointer to the actual node or to a struct value physically contained within that node through value-field paths. Named and anonymous value fields may hold components. Exclude the designated inheritance-parent subtree when establishing component ownership; pointer, interface, slice, and map edges are not ownership paths. Reject foreign objects, even when their types match. A component provider's type need not equal the level node's type.

Component paths name explicit direct field steps relative to the owning node, using the field's declared name even for an anonymous alias; promoted-selector shortcuts are not paths. `"."` remains the node slot. A component slot is identified by its declaration lineage, owning node type, and exact path, not by provider type. Initialization requires one node reference per level even when that node registers no operation, and one component reference per distinct registered slot; references may be supplied in any order. Several operations on one slot share its reference. Definition-created references may precede preparation and work with dynamic or precomputed Plans of that lineage. Reference factories do not prepare, validate, freeze, record sticky declaration errors, or retain instance pointers in reusable metadata.

One provider may supply several operations at its owning level. Different providers at that level may supply different operations, such as A1.Process and A2.Validate. Each operation may be registered at most once per level, including across providers or registration groups. Any second retained registration of an operation at one level is a DuplicateBinding, regardless of registration validity or order. A valid registration still satisfies that operation's coverage even if another registration is invalid; duplicates always invalidate the definition. The same provider cannot belong to two inheritance levels. Unrelated fields contribute no implementations unless explicitly registered.

Components do not become additional inheritance levels. They share their owning level's contracts and dispatch position; the physical parent chain remains single inheritance.

Each participating node/provider directly embeds a value Node, not a pointer or merely a promoted ancestor Node. The holder field must be exported: Node itself or an exported alias of it. Validation reports MissingNode for a holder embedded under an unexported alias name. Bodies use their own `receiver.Node.Scope()` holder. Init installs that holder's fixed level and complete-object reference. Node has no application state. Its scope identifies the actual owning level, without relying on an ancestor's promoted holder. The holder and copying safeguards are designed in architecture.md.

## S6. Validation, plan preparation, and reuse

Keep three concerns distinct, even if a future fluent operation coordinates them:

| Concern | Required work | Frequency |
| --- | --- | --- |
| Hierarchy validation | Verify the definition's structure, public/private contracts and extensions, capability identities/signatures, explicit registrations, ownership paths, supported storage/receiver forms, duplicates, and final target's method coverage | Definition-level work performed when that immutable definition is first prepared for reuse; not repeated for each object using its Plan |
| Plan preparation | Produce complete, immutable metadata from a successfully validated definition; optionally include precomputed resolution destinations | Once for a reusable prepared definition; optional conversion produces an equivalent reusable resolution variant |
| Instance initialization | Associate a concrete leaf and its actual embedded nodes/providers with an existing validated Plan; check instance invariants and install their scopes | For every independently constructed object, including every object using a cached Plan |

Validation establishes that the definition is valid; preparation materializes reusable metadata. A validated definition alone is not an initialized object. A Plan is usable only after validation and preparation succeed. Invalid definitions must produce structured errors before any object is initialized from them, and failures must publish neither a partial Plan nor partial instance bindings.

### Eager and lazy preparation

Support both strategies for the same hierarchy definition and fluent configuration:

- **Eager:** validate and prepare during application startup, without constructing an application object, then reuse the Plan for subsequent objects.
- **Lazy:** validate and prepare when the hierarchy is first needed, including during first-object setup, then reuse the Plan for subsequent objects.

Eager validation is optional. Lazy preparation is not an invalid or unvalidated initialization path: it must obtain a successfully validated, prepared Plan before the instance-binding stage proceeds. No separate hierarchy declaration or duplicated configuration may be required to switch strategies. Neither validation nor plan preparation invokes application constructors or methods.

Both strategies have identical inheritance semantics and initialized-object behavior, including dispatch, parent calls, state ownership, visibility, and application errors. Preparation timing and cost, and therefore the time at which an invalid definition is reported, differ. Eager preparation can report invalid definitions at startup even if no object is constructed; lazy preparation reports them on first need. An unused lazy definition need not be validated at startup.

### Plan ownership and caching

Reuse successful validation and prepared metadata across objects rather than repeating definition-level work on every initialization. This is reuse within a retained definition/Plan context, not a requirement for process-wide deduplication: separately managed contexts may prepare equivalent definitions. A changed definition needs its own validation and prepared metadata; it cannot mutate an existing Plan or silently reuse incompatible cached results.

Reusable plans and any cached preparation metadata must never retain application instances, receivers, Node holders, dispatch scopes, bound methods, or object-capturing closures. This includes references to any concrete object temporarily available during configuration or preparation. Only per-instance bindings retain that instance's actual subobjects. Independent objects may share immutable Plans and resolution tables, but must not share instance-specific receivers, pointers, or scopes.

Cache identity must account for the complete definition: selected target, ordered levels and node types, parent paths, every level's effective public/private contracts, canonical capability identities and signatures, explicit operation registrations, provider types, and provider ownership paths/levels. The leaf Go type alone is insufficient. Optional resolution variants must also be distinguished so a precomputed request cannot receive a dynamic lookup path. Cache keys and representation are implementation choices, not public API commitments.

Cached Plans must be safe for concurrent reuse. Concurrent first use must coordinate preparation/publication so no caller sees incomplete metadata or another object's bindings. A cache hit never bypasses per-instance validation of actual type/address ownership, nils, directly embedded holders, or prior initialization. A failure for one instance must not invalidate a valid shared Plan or alter another object.

Successful preparation is reused by concurrent definition-based callers, subject to sticky declaration errors recorded before each call is processed. Failed preparation publishes and caches no Plan; a later request retries the current definition, which remains editable after a nonsticky failure. Definition and level-handle operations are individually synchronized, including validation and reference creation, but a sequence of configuration calls is not an atomic declaration transaction. Preparation may encounter an incomplete configuration or freeze a valid intermediate one. Finish configuration before concurrent first use.

Do not mandate a global cache, a particular synchronization mechanism, or a cache lifetime/eviction policy. Precomputation remains optional under S7. The lifecycle and ownership responsibilities are described in [architecture](architecture.md#validation-plan-preparation-and-instance-initialization).

## S7. Resolution and precomputation

Both dynamic and precomputed resolution must implement the following behavior. Number levels root-first. Virtual resolution returns the greatest level explicitly registering T. Parent resolution from L returns the greatest registered level strictly below L, skipping absent implementations. Invoke that level's actual provider, never a leaf pointer that happens to promote it.

The body/provider's own scope determines subsequent parent calls. C.Process → A.Process still lets A virtually select B.Validate. Parent calls inside A start below A, not below C. A parent call to another operation also starts below the executing level. For component providers, this is the owning inheritance level: ParentMethod from A1 does not search a sibling A2 at the same level. Recursive virtual calls restart at the leaf; parent delegation descends; callbacks never change scopes.

Unknown capability requests panic with UnknownCapability; a known capability with no eligible ancestor panics with NoParentImplementation. Application signatures gain no framework error result. These must be distinguishable typed diagnostics. Calls through an uninitialized scope panic with Uninitialized. `Node.Virtual` and `Node.Parent` also panic with Uninitialized when called on a nil holder; `Node.Scope` on a nil holder is unchanged and carries no such guarantee.

A precomputed Plan must select the same provider as dynamic resolution for every operation and virtual/parent starting position. Missing ancestors are valid metadata, not conversion errors. This includes operations absent at intermediate levels and operations supplied by different components at one level. The table representation belongs to architecture.md.

Precompute is pure: it changes no source plan, scopes, or objects; invokes no application methods; publishes no partial result on failure; and is semantically idempotent. Existing objects retain their plan. It is safe to convert an immutable plan while other objects use it. Precomputed invocation must not scan the hierarchy or silently fall back to dynamic lookup. Results, traces, side effects, errors, and ownership must match the dynamic oracle.

Plan.Precompute returns an immutable converted Plan or a typed error; MustPrecompute panics with that error. Nil and unprepared Plans report InvalidPlan. Repeating conversion on a precomputed Plan returns that Plan. Repeated conversion of a dynamic Plan may create equivalent independent results; callers may retain a converted Plan for reuse. Converted Plans preserve definition lineage and accept its provider references.

Production precomputation operates on Plan, before binding an instance. A fluent lifecycle operation may select the converted Plan for subsequent initialization while preserving the source Plan. This does not require a second resolution engine or mutation of a live object. Live mode switching and mixing modes among one object's scopes are unsupported.

## S8. Visibility, lifecycle, and concurrency

Constructors publish a dedicated unexported public wrapper with named unexported storage, never an embedded implementation or Node. Its dynamic method set contains only final public operations. Private type assertions must fail. Internal leaked implementation/provider pointers retain their exported methods. External consumers are supported; cross-package derivation is deferred.

The lifecycle separates hierarchy validation, reusable Plan preparation, and initialization of an allocated leaf. Preparation may be eager or lazy under S6. Fluent configuration presents these concerns coherently. Invalid setup changes no existing scopes, including those already initialized and causing rejection. See the state transitions in architecture.md.

Install all scopes exactly once under exclusive instance initialization access, then publish. A second Init, even through another alias of the same object, returns AlreadyInitialized without replacement. Concurrent setup of the same target is unsupported; concurrent setup of different targets sharing one Plan or triggering lazy preparation of the same definition is supported.

Published plans, tables, object bindings, and scopes are immutable. Concurrent/reentrant dispatch is supported; application state, callbacks, and input data need their own synchronization. No global, goroutine-local, or object-local mutable current-level cursor is allowed.

Initialized nodes, ancestor values, and component providers must not be copied. Copies would retain references into the original object. Interface/plan/scope handle copying aliases the original and is allowed; it does not clone state. noCopy is advisory; reflection and all legal Go copies cannot be universally prevented or detected. Rebinding and cloning remain deferred.

## S9. Errors, verification, and excluded scope

Use deterministic exported typed errors compatible with errors.Is/errors.As, with stable codes and structured context. The error representation is designed in architecture.md. Must variants panic with the same error object returned by error-returning APIs. Deterministically report all missing mandatory methods. Do not match errors solely by text.

Distinguish at least InvalidDeclaration, InvalidHierarchy, InvalidContract, ContractExtension, ContractCollision, InvalidCapability, CapabilityIdentity, SignatureMismatch, UndeclaredOperation, DuplicateBinding, MissingMethods, InvalidProvider, MissingNode, ProviderOwnership, InvalidPlan, BindingMismatch, AlreadyInitialized, Uninitialized, UnknownCapability, and NoParentImplementation. Diagnostic context must identify the target, level, provider path, contract/capability, and expected/actual signatures where relevant. Exact prose is not an API; codes and structured meaning are.

For component references, an unknown owning node type, malformed reference, nil pointer, or wrong provider type reports InvalidProvider; a known owner with an undeclared component path or a missing/duplicate required slot reports BindingMismatch; a correct-type foreign address reports ProviderOwnership. Existing lineage and unusable Definition/Plan errors apply. An owner type absent from the hierarchy uses Level = -1. When the owning level's location is known, provider diagnostics use leaf-relative paths and holder diagnostics append the name of the directly embedded Node field: Node itself, or the alias name for a holder embedded through an alias; a missing holder, or a type with more than one, appends Node. If invalid structure or an unknown owner prevents establishing a prefix, retain the supplied path rather than inventing one.

Acceptance evidence is defined in testing.md. Arbitrary external providers, pointer inheritance, cross-package derivation, live mode switching, and cloning are deferred. Multiple providers are required by S5; fluent configuration and grouped registration are design goals under S1, not excluded features.

The minimum supported Go version is the version declared in go.mod. Toolchain coverage and performance verification belong to testing.md.

## S10. Optional code generation

heirygen is an optional command in this module. It reads specifications from Go source and writes ordinary Go source that uses the public API of S1–S9 and nothing else. It adds no library API, changes no library behavior, and replaces no check: every compile-time, validation-time, and initialization-time check of handwritten use applies unchanged to generated code. Handwritten use remains fully supported, and a limitation of the generator is never a restriction of the handwritten API. Reading source happens at generation time only; generated code performs no source inspection, reflective invocation, or unsafe operation. [ADR 0013](decisions/0013-optional-code-generator.md) records the decision, and [architecture](architecture.md#optional-code-generator) its design.

**Input.** The command reads the Go files of one package directory. A specification is the value of a string constant whose doc comment contains the line `//heiry:spec`; the declaration names one constant with one string literal. No comment, file, or other carrier is a specification, and a `//heiry:spec` line anywhere else is an error. The grammar has eleven line forms:

```text
import <name> "<path>"
operations <Contract>... [prefix=<p>] [suffix=<s>]
existing <Method> <Type>
hierarchy <Name> <LeafType> [from=<Name>] [omit=InitPlan]
chain <Name> [from=<Name>]
part <Name>
level <NodeType> [parent=<Field>] [public=<Type> private=<Type>]
node <Operation>...
component <path> <ProviderType> <Operation>...
use <Part>
wrapper <Type> [field=<name>] [holder=<Field>]
```

The hierarchy's levels and their order, each level's contracts and parent field, every registration with its provider type and path, and the wrapper come from the specification texts alone: its own, and those it takes lines from with `from=` or `use`. A level without `parent=` uses the field name an anonymous field of the preceding node type has; a level without contracts uses the preceding level's; a wrapper uses `field=state` and `holder=Node` unless given. A hierarchy's leaf must be its last level. A leaf spelled exactly as its last level is accepted; otherwise the two are compared as types, with parentheses dropped, each package name replaced by the import path it stands for, and local aliases followed, also inside type arguments. Only an alias declared once in the package and without type parameters is followed, and its right side is read with the imports of its own file. A leaf that is refused gets the reason: a name the package does not declare, declares more than once, declares as a type of its own, or declares with type parameters; a name of another package, whose aliases are not read; a cycle of aliases; or an alias whose right side uses a dot-imported name or an import whose package name cannot be read from its path. Method signatures of generated operation interfaces and forwarders come from the handwritten contract declarations, read as syntax. The generator never type-checks, never reads a provider's methods, and never infers a registration.

**Shared levels and parts.** A `chain` line starts a named run of levels, with the `level`, `node`, `component`, and `use` lines after it; a chain has no leaf, wrapper, or helpers, and generates no declaration. A `part` line starts a named group of `component` lines, which are the only lines that follow it. A `use <Part>` line, among the lines of a level of a hierarchy or chain, adds the part's component lines to that level at its own position, with paths relative to that level's node, as if they were written there; lines with one path at one level merge into one slot, whether they come from the level or from parts. Two provider types for one slot, compared as written, are refused: from two lines of one constant while it is read, and from lines of two constants at the later line in written-out order, naming both constants. `from=<Name>` on a `hierarchy` or `chain` line names a hierarchy or chain of the same package clause: the levels of the one that has it start with every level of the named one, with their parent fields, contracts, and registrations, and its own `level` lines follow. The first of them follows the last taken level as consecutive levels do, so its default parent field and contracts are that level's. `from=` takes nothing else: not the named hierarchy's name, leaf, `wrapper` line, or `omit=`, nor the `operations`, `existing`, and `import` lines of its constant. A constant holds at most one hierarchy, chain, or part, besides any `import` and `operations` lines, which precede a part line. Hierarchy, chain, and part names are unique together in each package clause; a chain or part name declares nothing in Go and may equal a Go name of the package. `from=` names a hierarchy or chain, and `use` a part; another kind is refused. A taken line keeps the meaning its own constant gives its package names, and each constant must use each of its own import lines. A hierarchy with `from=` may have no level of its own: it generates a second definition, whose leaf is the last taken level. Every chain with no level of its own is refused, and so are a part with no component line and a `from=` that names a hierarchy with no level of its own. A chain with `from=` and no level of its own, and a `from=` that names a hierarchy with no level of its own, name the target to use instead; the second leaves that advice out when the target would lead back to the hierarchy or chain whose `from=` names it. Also refused are a cycle of `from=`, a name that no hierarchy, chain, or part of the package clause has, and a name of the other package clause, the package's external test package or the package it tests, since neither can see the other's constants. Each constant that `from=` or `use` names must be compiled in every build that compiles the constant that names it: it is declared in the same file, in a non-test file without build constraints or a platform suffix, or in a file with exactly the same conditions, compared as written. The refusal is reported at that `from=` or `use` line. Once the links between specifications are checked, a problem reported at a line that hierarchies take names them in its message, so that it shows how far a fix reaches. A problem found for one hierarchy by its forwarder check, its repeated-guard check, or the check that each import name has one path names that hierarchy, with its path when it takes the line, and lists the others after "also taken by"; any other problem lists every hierarchy that takes the line after "taken by", each with its path. A path names each `from=` and `use` step as written. The `hierarchy`, `chain`, or `part` line of a constant counts as taken by every hierarchy that takes lines from it. Problems found while the files are read, and problems with the links themselves, carry no such list. [ADR 0014](decisions/0014-shared-chains-and-parts.md) records the decision.

**Output.** For each handwritten file that holds a specification, the command writes one file in the same package, selected by exactly the same builds, including constraints of legacy `+build` lines and of cgo. It contains, through the public API only:

- For each `operations` line, one single-method interface per method of the listed contracts, named prefix + method + suffix, except where an `existing` line names the interface that identifies that method. A line with such a method gives `prefix=` or `suffix=`; without either it is refused. A contract is listed by at most one line. In the package's generation input, with every file and build included, lines that name the same interface must give it the same method name; contradictory lines are refused, naming both. Lines that give one interface the same method reuse it. Interfaces are the same when their identity keys are, and keys are syntactic: a package-level name after local aliases are followed, or an import path and name.
- For each hierarchy, one Definition built with `Define`, one `Level[Node, Public, Private](parentField)` per level with the parent field written explicitly, one `Bind[Operation]` per registration with a typed-nil witness and its provider path, and `End`.
- A reference list and two initialization helpers per hierarchy, specified below.
- For a hierarchy that takes lines with `from=` or `use`, exactly the declarations of the same hierarchy written out in one constant, with every `from=` replaced by the levels it takes, every `use` by the part's component lines, and the import lines they use added, apart from the freshness assertions and the probes' comments. For a chain or part, nothing but its freshness assertion, beside what the `operations` lines of its constant generate, also when it takes lines; a file whose specifications hold only chains or parts still gets an output.
- For each `wrapper` line, an unexported struct type holding the leaf in one named unexported field, as S8 requires; one forwarder per operation of the leaf's public contract that resolves it virtually through the leaf's directly embedded holder; and an assertion that the wrapper satisfies the public contract.

Each output imports exactly the packages its own code uses, under the names that code uses, and binds each import name to one path: a name bound to two paths in one output is refused, naming both bindings, a specification's import line or a Go file's import declaration.

A forwarder resolves the interface its `operations` line gives the method. When the hierarchy registers that method through another interface, generation fails and names the `existing` line that makes them one; a method that no level registers is not refused, and the library reports it as MissingMethods when the declaration is prepared. Where a registration spells that interface differently, through an alias, the output asserts at compile time that the two are identical. The holder must be the leaf's directly embedded `heiry.Node` value field, under its own or an alias name. The generator establishes it from the struct the leaf is declared as, reading through local aliases, type definitions, generic instantiations, and parentheses; when it cannot establish exactly one such field, it refuses the wrapper, and a hierarchy without a `wrapper` line, with a handwritten wrapper, is still generated.

**Guards.** The output carries compile-time assertions that make the demonstrated classes of stale input fail ordinary compilation:

- The specification is still a constant and still has the text the file was generated from, and so does every constant that a hierarchy takes lines from, directly or through another constant, with `from=` or `use`, each once. After an edit to such a constant, every output that still holds its old lines fails ordinary compilation, also after a run that put only some of the outputs in place.
- Every listed contract has exactly the methods, with identical signatures, of its operation interfaces, and every `existing` interface still has exactly the one method it identifies. The output of a hierarchy repeats that last check for each `existing` interface its registrations or wrapper use from an `operations` line in another file, so every build that compiles them checks it, and for each registration in its own file whose spelling differs from that file's `existing` line, such as a local alias, which could later name another interface without any change to the specification. Both of the leaf's contracts of every generated wrapper must be listed.
- Both of the leaf's contracts of every generated wrapper still have exactly the methods recorded when the wrapper was generated. This assertion is in the wrapper's own output, so every build that compiles the wrapper checks both contracts, wherever the `operations` lines are and also when the private contract had no method.
- No method of a generated wrapper is named after an operation of the leaf's private contract, checked against that contract itself.
- The holder each forwarder dispatches through is still a `heiry.Node` declared in the leaf itself. A stale edit of the leaf that gives the holder's name to a pointer, which could point into another object, or leaves only a holder promoted from an embedded struct, by pointer or by value, fails compilation. A stale edit that leaves a directly declared named `heiry.Node` value under the holder's name is a documented limit: it compiles, the wrapper's first call panics with `Uninitialized`, and check mode or regeneration detects it.
- The leaf is still its last level's type: the references pass the leaf to the last level's reference factory, so a leaf accepted through an alias that now names another type fails compilation.
- Each level's parent field, and the first field of each component's path, is still declared in its own struct, the level's node or the component's owner, with the type the specification gives it. A field reached only through another embedded struct, as when the specification leaves out a level or a level is inserted in the structs alone, fails compilation, and so does a field that is gone or has another type. Later steps of a component path are in types the specification does not name, and the library checks them; it also checks that a parent field is embedded rather than named. In an output whose hierarchy takes lines with `from=` or `use`, each probe's comment names the constant that holds its level or component lines, and the probe of the first level of a constant whose levels follow another constant's names both, since a missing level can go in either. A component probe names each constant that holds lines of its slot once, and for a part's line also the constant of the `use` line, since the part may be used at a level whose node lacks the field.

No guard may depend on an identifier the package could redeclare to disarm it. The satisfaction assertion is not an exact method-set check: a wrapper may carry further handwritten methods, and a handwritten method with another name can still call a private operation. Equivalent spellings of one signature, with other parameter, result, or type alias names, are accepted; type identity is decided by the compiler through these assertions.

**Initialization helpers.** For a hierarchy `H` with leaf `L`, `HRefs(*L)` returns one reference created by `H` for every level node and registered component slot, with its owner type and path explicit. `HInit(*L)` is `H.Init` with those references and prepares lazily. `HInitPlan(*Plan[L], *L)` is `Plan.Init` with the same references, so it accepts dynamic and precomputed Plans of `H`'s lineage and rejects a Plan of another definition with BindingMismatch even when its slots coincide. For a nil object the references point into a scratch value, so `Init` reports the nil object as it does for well-formed references: InvalidProvider with the target and no level, path, or types. Unusable Plans, invalid definitions, repeated initialization, foreign or misplaced providers, and atomicity behave exactly as for a direct `Init` call; every ownership check happens in the library's binder. `omit=InitPlan` on the hierarchy line leaves out `HInitPlan` and nothing else.

**Trust boundary.** Existing compiler and library checks remain mandatory, and the guards detect the demonstrated classes of stale input. That a generated file corresponds to its specification also depends on the generator being correct. Check mode detects output that differs from what the generator version being run would emit. Neither check mode nor tests are described as compiler guarantees or as proof against generator defects.

**Command.** Generation works whether the generated output is absent, stale, or does not compile; handwritten files must be syntactically valid and need not type-check. Output is deterministic and formatted. A generated package-level name that the package already declares, or that the generator refuses, an unsupported input, or an ownership conflict is reported with its position before any file changes. The generator refuses `init` and `_`, a predeclared identifier, and a name that an import of one of the package clause's files binds: its explicit name, or else the last element of its path, or the element before a major-version element such as `v2`. When a package's name differs from that element, a clash with it is not detected, and a name equal to the element is refused. An output name that differs only in case from another file of the directory is an ownership conflict, except for an obsolete owned output whose source was renamed in case only, which the new output replaces. Every output is put in place as a whole file, one file at a time; the set of outputs is not replaced atomically, so a failure partway can leave some outputs new and the others as they were, and a rerun completes the rest. A new output, including the new name of a case-only rename, never replaces a file that appears while the command runs; this needs hard links, so on a file system without them a run that has such an output to put in place fails before any output changes, and a run that only replaces or removes existing outputs needs no link. An existing output is replaced or removed only if it is still the file that was read. No other program may change the command's existing outputs while it runs, for example through an overlapping run or a branch switch: a change between that check and the replacement or removal is not detected and is lost. If a case-only rename cannot be completed and a file has taken the old output's name meanwhile, that file is kept, and the old output is kept under a hidden name that the error reports together with the step that recovers it. The command owns only files that carry its marker for the source file they belong to; it never overwrites or deletes another file, and refuses to proceed when one would be replaced. All output is validated and rendered before any file changes, each file is replaced whole so no output is left partial, and owned outputs whose source no longer holds a specification are removed. A run that is interrupted, for example killed, can leave the command's hidden files, which the go command and later runs ignore; a case-only rename interrupted after moving the old output aside leaves it only under its hidden name, and a rerun creates the new output. A read-only check mode writes nothing and reports missing, differing, and obsolete outputs. Outputs are written with LF line endings; a marker line ending in CRLF is recognized, and existing outputs are compared with CRLF read as LF. Exit statuses are 0 for success, including a request for the usage with `-h`, 1 when check mode finds outputs that are not up to date, 2 for a usage error, and 3 when generation or checking cannot be completed. The command is supported on Linux, including WSL2 with the package on the Linux file system, and on macOS. Native Windows, and Windows drives accessed from WSL, are neither supported nor tested. This restricts only where the command runs: the library and generated code are plain Go and carry no platform restriction.

**Unsupported inputs**, each refused with a diagnostic, besides the refusals of shared levels and parts above: contracts that embed an interface of another package or a predeclared identifier the package does not declare, generic contracts and methods, type-set elements, a contract declared more than once in the directory, a contract that embeds an operation interface generated from it, a wrapper whose leaf contracts are not both listed, an exported wrapper or storage field, a wrapper whose leaf's directly embedded Node the generator cannot establish or whose holder names another field, a forwarder that would resolve another interface than the one its hierarchy registers for that method, a wrapper's hierarchy with a registration that cannot be matched to a method while a forwarded method has no matched registration, signatures that use names a dot import provides, unqualified specification types that the package does not declare, a leaf that the generator cannot show to be its last level's type, imports whose package name cannot be read from the import path, and a registration whose repeated guard the generator cannot show to compile in every build of its file. The last is conservative: the generator compares build conditions as written, without solving them, so an equivalent condition spelled differently counts as different, and it checks only the unqualified names of the signature it would copy. The generator reads every Go file of the directory regardless of build constraints, so one generated name serves all of the directory's build configurations.
