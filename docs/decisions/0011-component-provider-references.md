# ADR 0011 — Component provider slots and references

Status: accepted by the project owner for M8.

Decision: the existing `Definition[Leaf]` and `Plan[Leaf]` each add `ComponentProvider[Node, Provider any](providerPath string, ptr *Provider) ProviderRef[Leaf]`. A component slot is identified by the definition lineage, owning hierarchy node type, and exact provider-relative path. `"."` remains the node slot supplied through the existing `NodeProvider` method. The provider type is checked against the slot but does not identify it; two fields of the same type at different paths are distinct slots. One node reference per level and one component reference per distinct registered component slot are required, independent of argument order. Several operations registered on one slot share one reference.

Definition-created references may precede preparation and work with dynamic or precomputed Plans of the same lineage. Factories do not prepare, validate, freeze, or record sticky declaration errors. A malformed reference is rejected by Init with a typed diagnostic: unknown owner or malformed/nil/wrong-type provider uses `InvalidProvider`; known owner with an undeclared path and missing/duplicate slots use `BindingMismatch`; a correct-type foreign address uses `ProviderOwnership`. Existing lineage, unusable Definition/Plan, `AlreadyInitialized`, and `MissingNode` behavior remains. Diagnostics include a leaf-relative provider or holder path when the owning level is known.

Provider paths use explicit direct value-field names, including actual declared names of anonymous fields. They may traverse named or anonymous, exported or unexported struct values, but not pointers, interfaces, slices, maps, or the owning level's designated inheritance-parent subtree. Every participating provider directly embeds a value `Node`. Validation checks paths, types, registration signatures, ownership exclusions, and duplicate operations without constructing objects. Invalid registrations do not provide coverage; safe contract analysis continues and retains all discoverable missing methods.

The owner later clarified that safe analysis may continue after an invalid parent edge, without deriving a leaf-relative prefix through that edge or publishing a Plan. An unknown owner type uses diagnostic level `-1`. [Specification S5](../specification.md#s5-state-structure-and-providers) states the approved order-independent duplicate and coverage rule.

At each Init, the binder compares supplied pointers with the exact embedded addresses reached through validated paths, checks all distinct holders before writing any scope, and installs each holder once at its owning level. It uses a legitimate pointer supplied by the declaring package to access the component's exported direct Node; restricted fields are never extracted through `Interface()` or `Addr().Interface()`. Plans retain only receiver-free slot and resolution metadata. Dynamic and precomputed lookup continue to select an operation's actual provider at the chosen inheritance level, and parent calls start strictly below that level.

Alternatives: provider-type slot identity cannot distinguish same-type fields; level-handle-only factories would make standalone Plans depend on saved declaration handles; reflective extraction of unexported providers would violate Go reflection access rules; object-capturing selectors would expand the receiver-free metadata boundary. None is selected. The existing builder, validators, binder, and typed resolver remain the implementation machinery.
