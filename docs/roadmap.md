# Implementation roadmap

This document tracks implementation of the approved design. [AGENTS.md](../AGENTS.md) governs development; the [specification](specification.md) defines behavior, [architecture](architecture.md) defines responsibilities, and [testing](testing.md) owns implementation order and acceptance criteria. [ADRs](decisions/) preserve rationale. The roadmap does not replace any of them or authorize a new API.

Each milestone's status and evidence are recorded below.

## Order and dependencies

Work through M1–M9 sequentially, completing each gate before starting the next milestone. This mapping preserves the [existing TDD sequence](testing.md#gated-production-milestones):

| Roadmap | Testing stages | Relationship |
| --- | --- | --- |
| M1 | 1, then 2 | Prove two-level dispatch before three-level semantics |
| M2 | 3 | Bind actual embedded state and scopes |
| M3 | 4, then 5 | Establish contracts before structural/ownership validation |
| M4–M6 | 6 | Resolve the schema API, then implement dynamic Plan/lifecycle foundations and fluent configuration |
| M7 | 7 | Add concurrent lazy preparation, caching behavior, and precomputation |
| M8 | 8 | Extend the proven mechanism to multiple providers |
| M9 | 9 | Integrate, document, and demonstrate the implemented package |

Precomputation precedes multiple providers because testing.md already requires that order. M8 extends the equivalence tests and benchmarks to components. M5 delivers explicit reuse of an already prepared dynamic Plan; M7 extends that machinery with concurrent lazy preparation, caching behavior, and optimization. These subdivisions do not allow skipping the testing plan's internal gates or dropping later release requirements.

## Approval and completion gates

The owner approved M4's receiver-free declaration in [ADR 0007](decisions/0007-fluent-receiver-free-declaration.md), M5's dynamic preparation and node binding in [ADR 0008](decisions/0008-dynamic-plan-lifecycle.md), M6's grouped registration in [ADR 0009](decisions/0009-grouped-fluent-registration.md), M7's Plan conversion and concurrent preparation in [ADR 0010](decisions/0010-concurrent-preparation-and-precomputed-plans.md), and M8's component references in [ADR 0011](decisions/0011-component-provider-references.md). [ADR 0006](decisions/0006-receiver-free-schema.md) remains unapproved history.

The M5 node-reference API is approved in [ADR 0008](decisions/0008-dynamic-plan-lifecycle.md), and the M8 component-pointer integration in [ADR 0011](decisions/0011-component-provider-references.md). Do not infer further approvals from illustrative syntax, feasibility analysis, or this roadmap. Unspecified internal mechanisms are not additional roadmap requirements.

Every implementation milestone follows **Red → Green → Refactor** as required by AGENTS.md. Mark it Completed only when all of these are evidenced:

- [ ] Focused acceptance tests pass after an observed, meaningful Red result.
- [ ] Existing regression tests remain green.
- [ ] Applicable [static, test, race, and CI gates](testing.md#quality-gates-and-ci) pass on actual maintained source, subject only to the milestone-specific owner-approved local-gate exceptions recorded there.
- [ ] Documentation accurately describes the delivered behavior and remaining later milestones.
- [ ] Required owner decisions are recorded and no unresolved blocker affects the delivered functionality.

Code existence, documentation alone, empty package runs, and tests of a separate engine do not satisfy completion. Examples wait until M9; earlier development uses the actual package and its test fixtures, without an alternative implementation or unapproved public API.

## M7. Shared plans, precomputed resolution, and benchmarks

- **Status:** Completed — the owner directed a green CI designation and completion from passing local code and documentation gates for M7 specifically; acceptance, fuzz, and benchmark evidence is recorded below.
- **Objective:** Extend M5's reusable Plan and instance-binding machinery with concurrent lazy preparation, caching behavior, and the optional equivalent lookup optimization.
- **Scope:** Testing stage 7; [S6](specification.md#s6-validation-plan-preparation-and-reuse), [S7](specification.md#s7-resolution-and-precomputation), and S8 concurrency.
- **Deliverables:** Cache behavior with verified complete-definition identity, concurrent lazy preparation/publication, immutable precomputed Plans, precomputed fluent lifecycle coverage, and benchmark results. Reuse M5's preparation and binding machinery rather than implementing a second Plan-reuse or initialization path.
- **Dependencies:** M6 and a proven dynamic oracle; owner approval of the public signatures and concurrency policy recorded in [ADR 0010](decisions/0010-concurrent-preparation-and-precomputed-plans.md).
- **Acceptance criteria:** Complete [preparation/reuse acceptance](testing.md#preparation-and-reuse-acceptance), the applicable two-mode matrix, [exhaustive/fuzz checks](testing.md#exhaustivepropertyfuzz-tests), and [benchmark evidence](testing.md#benchmark-evidence). No receiver leakage, partial publication, live mode switching, or dynamic scan fallback. Record measured results without inventing performance thresholds or requiring a global cache.
- **Implementation:** `Plan.Precompute`/`MustPrecompute` build a separate receiver-free table of parent and virtual owner indices; a converted Plan keeps the definition lineage and uses the existing per-object binder and typed resolver. Dynamic Plans and previously initialized objects stay dynamic. A definition mutex serializes each declaration, validation, reference, and preparation operation through successful Plan publication; failed preparation is uncached and retried. The CI workflow now runs the bounded resolution fuzz target.
- **Observed Red → Green:** A focused conversion test failed to compile because `Precompute`/`MustPrecompute` were absent, then passed after implementation. A simultaneous lazy-Init race test produced data-race reports and different published Plan pointers, then passed under `go test -race` after synchronization. Additional tests passed on first run as acceptance coverage rather than retrospective Red evidence.
- **Review follow-up:** The independent oracle now calls both typed resolution modes from every parent start and every virtual start, asserting actual provider identity and structured missing-parent errors alongside table indices. It passed its first focused run; this is added acceptance coverage, not a new behavioral Red. Benchmarks now include an ordinary-interface public/private baseline and a different-operation parent-call scenario, and reset timing/allocation counters after one-time setup for validation, warm preparation, conversion, and per-object initialization. The benchmark smoke run passed. Stale precomputation status in architecture.md and ADR 0007 now points to ADR 0010.
- **Acceptance coverage:** Tests exercise eager and first-use schedules; dynamic/precomputed embedded state, pointer identity, skipped levels, root-only operations, parent calls to a different operation, recursion/reentry, private delegation, application errors, typed missing/unknown diagnostics, no scan fallback, unchanged dynamic objects, and receiver-free converted metadata. Separate valid definitions of one leaf type retain distinct dispatch; invalid same-leaf variants with parent/provider paths, intermediate contract narrowing, canonical capability identity, or provider type still fail despite a warm valid Plan. Prepared variants retain lineage and still reject foreign references/providers, repeat initialization, and partial scope writes. Concurrent first use, failed retries/repair, frozen-edit ordering, validation/reference creation, simultaneous conversion, read-only dispatch, and independent objects sharing one converted Plan pass the race detector. An external-package test compiles and runs chained and separate preparation/conversion/initialization through a public-only wrapper. An independent backward-search oracle exhausts nonempty single-capability layouts through depth 5 and two-capability layouts through depth 4, checking every parent/virtual position; bounded fuzzing covers larger layouts through depth 10.
- **Local verification:** On Go 1.27.1 (`darwin/arm64`, Apple M2), scoped formatting including maintained fixtures, nonempty root package discovery, `go vet .`, `go test . -count=1`, `go test -race . -count=1`, the package's positive/negative compilation and vet fixtures, `scripts/check_docs.py`, six checker tests, and `git diff --check` passed after the review follow-up. Scoped formatting, vet, unit/race tests, documentation checks, six checker tests, and diff whitespace checks passed again on the current tree before the M7 completion designation. The expanded bounded `FuzzResolution` command passed for 5 seconds and 109,522 executions. The documented `go test -run '^$' -bench . -benchmem -count=5 .` passed: 71 cases, five measurements each. The Go cache was set to writable `/tmp/heiry-go-cache`.
- **Benchmark evidence:** Refreshed five-run medians in ns/op for interface / dynamic / precomputed were depth-1 root-only (0.97 / 25.70 / 38.12), depth-3 sparse (0.95 / 34.63 / 39.75), depth-10 root-only (0.93 / 68.19 / 38.83), and depth-10 dense with five capabilities (0.91 / 22.66 / 37.11); these dispatch cases allocated 0 B/op and 0 allocs/op. Mixed receivers measured 2.24 / 24.08 / 57.49 ns/op. Public/private delegation measured 51.49 / 158.0 / 201.0 ns/op (interface 32 B/2 allocs, dynamic and precomputed 48 B/3 allocs). A parent call to a different operation measured 27.34 / 104.3 / 135.9 ns/op (each 16 B/1 alloc). Lifecycle medians: builder 637.9 ns/1505 B/20 allocs; validation 3387 ns/6104 B/39 allocs; preparation excluding builder 3685 ns/6392 B/42 allocs; lazy first use excluding configuration/object setup 4549 ns/7600 B/52 allocs; warm Prepare 12.66 ns/0 B/0 allocs; conversion 635.2 ns/528 B/6 allocs; per-object Init excluding leaf/reference setup 556.6 ns dynamic and 555.9 ns precomputed, each 1208 B/10 allocs. The earlier lifecycle timing figures included setup and are superseded by these isolated measurements. Precomputation helped the deep root-only lookup here but cost more for shallow, dense, mixed, and delegation scenarios; ordinary interface baselines may benefit from compiler devirtualization. Shared tables consume O(depth × capabilities) indices, while each object retains separate bindings.
